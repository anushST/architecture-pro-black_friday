# Миграция на Cassandra

## 10.1. Выбор данных для миграции

|Сущность|Решение|Причина|
|---|---|---|
|Orders|Cassandra|50к запросов/сек в пики, append-only модель|
|Order history|Cassandra|Time-series, только чтение и добавление|
|User sessions|Cassandra|Высокая скорость записи, нужен TTL|
|Product views|Cassandra|Аналитика, огромный объём, eventual consistency OK|
|Products|MongoDB|Транзакции для остатков, сложные запросы|
|Carts|MongoDB|Частые обновления, нужна атомарность|

**Обоснование:**
- Orders — критична скорость записи в пики, заказы не удаляются
- Sessions/Views — не требуют строгой консистентности, важна скорость
- Products — нужны транзакции при списании остатков, Cassandra не подходит

## 10.2. Модель данных

### Orders — две таблицы

**orders_by_id:**
- Partition key: order_id (UUID)
- Для получения заказа по ID
- UUID равномерно распределяет нагрузку

**orders_by_user:**
- Partition key: user_id
- Clustering keys: created_at DESC, order_id
- Для истории заказов пользователя
- Все заказы пользователя в одной партиции — быстрое чтение
- Даже активный пользователь не создаст слишком большую партицию

### User Sessions
- Partition key: session_id (UUID)
- TTL: 24 часа (автоочистка)
- UUID равномерно распределяет сессии

### Product Views — с bucketing
- Partition key: product_id + view_date + bucket
- Clustering key: view_hour
- Counter для подсчёта просмотров

**Bucketing (bucket 0-3):**
- Популярный товар распределяется по 4 партициям
- Предотвращает горячие партиции
- При чтении суммируем 4 бакета

## 10.3. Стратегии консистентности

### Уровни консистентности
|Таблица|Write CL|Read CL|Обоснование|
|---|---|---|---|
|orders_by_id|QUORUM|QUORUM|Критична точность данных|
|orders_by_user|ONE|ONE|История может иметь задержку|
|user_sessions|ONE|ONE|Скорость важнее точности|
|product_views|ONE|ONE|Аналитика, eventual consistency OK|

**QUORUM** = большинство реплик (2 из 3)  
**ONE** = достаточно одной реплики

### Hinted Handoff
**Применяем:** sessions, views  
**Суть:** при недоступности ноды запись временно сохраняется на другой, потом отправляется  
**Зачем:** не блокирует запись, eventual consistency приемлема

### Read Repair
**Применяем:** orders_by_user, sessions  
**Суть:** при чтении сравнивает версии на репликах и синхронизирует в фоне  
**Зачем:** данные читаются часто, постепенно "лечит" расхождения

### Anti-Entropy Repair
**Применяем:** все таблицы периодически  
**Расписание:** orders еженедельно, history каждые 3 дня  
**Суть:** полная синхронизация всех данных между репликами  
**Зачем:** гарантирует eventual consistency, находит все расхождения

## Конфигурация

**Replication Factor:** 3  
**Топология:** 3 ДЦ × 3 ноды
**Почему RF=3:**
- QUORUM требует 2 из 3
- Выдерживает падение 1 ноды
- Баланс надёжности и overhead
