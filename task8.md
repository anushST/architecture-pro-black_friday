# Задание 8. Выявление и устранение «горячих» шардов

## 1. Метрики мониторинга

### Что отслеживать

**По каждому шарду:**
- Операции чтения/записи в секунду
- Использование CPU и памяти
- Количество чанков
- Размер данных

**Критические пороги:**
- Разница нагрузки между шардами > 40% — тревога
- Jumbo chunks > 0 — проблема с шард-ключом
- Разница в количестве чанков > 30% — нужна балансировка

### Как мониторить

Проверять каждые 5 минут через встроенные команды MongoDB или использовать Prometheus + Grafana для визуализации.

Настроить алерты при превышении порогов.

## 2. Причина проблемы
**Ситуация:** 70% запросов на один шард из-за категории "Электроника"

**Причина:** неправильный шард-ключ, включающий category

Если ключ содержит category, все товары одной категории попадают на один шард. Популярная категория создаёт hotspot.

## 3. Решение
### Правильный шард-ключ
**Использовать:** hashed product_id
**Почему работает:**

- Товары любой категории равномерно распределяются
- Нет привязки к значению category
- Популярные товары автоматически балансируются

### Процесс исправления
1. Создать новую коллекцию с правильным ключом
2. Скопировать данные
3. Переключить приложение
4. Удалить старую коллекцию

**Временные меры:**
- Перевести чтение на реплики
- Добавить кеш для популярных товаров

## 4. Автоматическое перераспределение

### Балансер

**Настройки:**
- Всегда включен
- Размер чанка: 32 MB (вместо 64 MB)
- Окно балансировки: ночные часы (опционально)

**Как работает:**  
MongoDB автоматически перемещает чанки с более загруженных шардов на менее загруженные, когда разница превышает 8 чанков.

### При обнаружении hotspot

**Сразу:**
- Включить чтение с реплик
- Активировать кеш

**В течение дня:**
- Принудительно запустить балансер
- Пересоздать коллекцию с правильным ключом
